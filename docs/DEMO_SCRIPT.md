# IntelliFile: demo script and viva questions

Length: about 7 minutes. Setup before the audience arrives: extract IntelliFile-windows.zip to a fresh folder, close browsers (Ask is slower with little free memory), plug in the laptop, note the fallback screenshots in docs/screenshots/ui. Do not press Open, or Enter twice on the same search: Open launches another program on the desktop. Do not use Ctrl+Enter (opens File Explorer).

## Viva questions and short honest answers
1. **Where is the agent?** Three parts: the Ask agent (a local Qwen2.5-1.5B that plans searches and reads), the adaptive router (chooses the cheapest search per query) and memory/personalization. File watching and power-aware indexing are autonomy, not AI agents.
2. **What strategy choice does the agent really make?** After a first-look search it chooses: search again with other words, mode (keyword or smart) or filters, read more of a source, or answer. It can split two-part questions. The trace shows each step.
3. **Why not use a big cloud model?** The requirement is offline and private. The cost is a small model that is slower and sometimes loose, so the code does the checking.
4. **How do you stop hallucinations?** The code picks the sources that support the answer, drops extra citations, checks every number is in the sources and checks the question's premise. An unsupported answer becomes "I couldn't find that in your files". Result: 0 false answers on 5 unanswerable questions, 25/25 grounded.
5. **Is the router better than always using hybrid?** Same accuracy (100% top-5, MRR 0.964), about 76% of the time, embedding model on 43% of queries against 97%. The gain is on file-name and keyword queries; hybrid queries cost slightly more.
6. **Isn't the router just tuned to your test queries?** Partly, yes. The rules were set on the same kind of labelled queries; 60/60 tier match is optimistic. A learned router did no better (77.6% both).
7. **Why is the reranker not used first?** Measured: on every query it costs about 7 times the median latency (129.6 vs 17.1 ms) and changed no result, so it only runs when nothing is confident.
8. **How is personalization measured?** 18 ambiguous searches with near-identical twin files and a generated four-week history: habitual file first 100% vs 39% off; 0 of 42 other searches worse. Limit: synthetic history, no real users.
9. **Why so conservative, only near-ties?** Reordering every near-tie by habit pushed the right answer down on 6 of 42 ordinary queries. Restricting it to near-duplicate passages gave 0 harm.
10. **What can it learn from?** Its own searches, opens and clicks, and optionally Windows' Recent items (off by default). It can be cleared in Settings.
11. **How do you know it is offline?** An offline guard in tests refuses and counts any non-loopback connection: 0 in every run. The shipped app has no code that connects out; the guard is only a test tool.
12. **What stops another program or web page reading the index?** The engine listens on 127.0.0.1 only, checks the Host header, and needs a random per-launch token on every request (401 otherwise). The app page has a content security policy, and the app may only open files inside indexed folders and never programs.
13. **What are the weak spots?** Photo search on near-identical pictures (first 50% on 26 real photos), Ask taking 20 to 45 s on a busy laptop, a small model that can misstate non-numeric facts (2 of 25 cited the wrong file), and the results being from generated data.
14. **What has not been tested?** The zip on a second clean Windows PC, voice with a real microphone, unplugging mid-index, Ctrl+Space from another program. Two tests were flaky once (a power test, a cold start) and were not loosened.
15. **What would you do next?** Run the clean-PC test, test on a real person's files and history, try the 3B model, and run the CI build.
