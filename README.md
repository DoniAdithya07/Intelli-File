


# IntelliFile — Project Tracker

Intelligent local file search & recommendation system for Windows and macOS. Full spec lives in [`Implimentation_plan.md`](./Implimentation_plan.md); this file tracks build progress phase by phase.

**Status legend:** ✅ Done · 🚧 In Progress · ⬜ Not Started


> ⚠️ **Grading constraint:** the professor downloads the built app and runs it on his own laptop to grade it (50% of course grade) — no dev environment, possibly no GPU, possibly no admin rights, possibly no internet, and no one there to explain anything. **Both a Windows and a macOS build get graded/tested** — this doubles the Phase 14 packaging/clean-machine-testing work (a real Windows `.exe`/`.msi` build AND a real macOS `.app`/`.dmg` build, each tested on a machine that isn't the dev machine). Packaging and offline reliability are graded requirements, not polish. See Phase 14.

> 🎯 **The assignment (added 2026-09-21, verbatim from the professor — "Project 5: Agentic AI-based Intelligent File Recommendation").** *Design and implement an Agentic AI-based Intelligent File Recommendation and Retrieval System that understands natural-language user queries, analyzes user file-access behavior and working context, and dynamically selects and optimizes appropriate file retrieval and reasoning strategies. The system should integrate filename, metadata, keyword, semantic, and hybrid search with reranking and LLM-based reasoning to identify, rank, and recommend the most relevant files. It should personalize recommendations using recurring work patterns, frequently accessed files, preferred file types, topics of interest, and temporal usage patterns, while intelligently routing each query through an efficient retrieval pipeline to maintain high retrieval quality and minimize unnecessary computation and latency.*
>
> - **Objective 1 — Intelligent File Discovery and Recommendation.** An agent that understands natural-language file queries, identifies the appropriate retrieval strategy (filename, metadata, keyword, semantic or hybrid), and retrieves, ranks and recommends the most relevant files with explanations.
> - **Objective 2 — Personalized File Recommendation Using User Context.** Analyze historical file-access and activity patterns; identify frequently accessed files, recurring work patterns, preferred file types, topics of interest and temporal usage patterns; use them to personalize retrieval and recommendations for the current query and working context.
> - **Objective 3 — Agentic Query Optimization and Retrieval Routing.** Estimate each query's complexity; dynamically select the combination of metadata search, keyword search, semantic search, hybrid retrieval, reranking and LLM reasoning; keep quality high while cutting unnecessary computation, processing time and latency.
>
> **How the phases map to it (honest, 2026-09-21):** Phases 0–9 build the retrieval foundation Objective 1 needs (filename, `type:` metadata, BM25, semantic, hybrid RRF, explanations) — but no *agent* chooses the strategy, the user picks a mode by hand. **Objectives 2 and 3 have nothing built** — no usage is logged, no reranker, no LLM, no routing. Phases 16–20 below are the missing core and are built **before** Phases 10–14 (polish/packaging). Voice, photo and video search (Phases 7, 8, 8b) are outside the brief — kept as extras, not expanded further.

**Two real findings from building this, both caught by verifying instead of assuming:**
1. **The text tower takes only `input_ids` — no `attention_mask`.** Checked the actual ONNX signature rather than trusting the usual transformer convention. That matters because CLIP pools its text output at the end-of-text token's position, so batching with padding could silently shift that position and corrupt the embedding with no error. Text is therefore encoded one string at a time (search embeds a single query anyway, so nothing real is lost).
2. **LanceDB returns *squared* L2 distance, not L2.** The relevance cutoff was initially derived from plain L2 and filtered out *every* correct match — the prototype caught it immediately. Verified empirically (cos 0.3033 → distance 1.3964, exactly 2×(1−cos)) and re-derived from measured values: correct matches land at 1.35–1.40, the same query against a wrong image at 1.50–1.51, an unrelated query's best hit at ~1.48.

**Verified with `backend/scripts/prototype_visual_search.py`** (8 checks, all passing): real generated image fixtures (no committed binaries, no network) get discovered and routed to CLIP while a text file in the same folder correctly goes to the text pipeline; three distinct typed descriptions each rank their own photo first; a text file never leaks into visual results; an unrelated query stays measurably further away (asserted as a *relative* comparison, not "returns nothing" — an absolute cutoff is a hand-set heuristic that can't be honestly tuned against flat synthetic shapes); capture-date and kind metadata populate; thumbnails render as valid correctly-resized JPEGs; deleting a photo removes it; and tombstone cleanup purges photo vectors too. Also verified live over the real HTTP API (index → search → thumbnail, plus the 404/422/empty-query error paths). Full 8-phase regression afterward — all still passing.

**Real-photo test (2026-09-11) — found and fixed one real bug.** Indexed 28 real images through the live HTTP API (20 phone photos from a birthday, 3 illustrated character cards, a university logo, a QR code, 3 camera-calibration checkerboards — copied to a temp folder, records purged afterwards). Unrelated queries ("mountain landscape", "a dog running on the beach") correctly returned nothing or one weak hit. 28 images indexed in 1.7s on CoreML.

**Model upgrade + a reproducibility bug, 2026-09-11 (user's live test: "airplane" ranked an aerial airport photo above the actual planes).** Downloaded all three Xenova CLIP exports and measured them on the labelled set (`scripts/download_clip_model.py` now takes a variant):

| variant | size | CPU ms/img | best F1 | ranking p@n | "airplane" |
|---|---|---|---|---|---|
| ViT-B/32 (was) | 149 MB | 9 | 0.74 | 0.74 | plane wreck, airport, then the planes |
| **ViT-B/16 (now)** | 154 MB | 37 | 0.77 | 0.74 | planes first; all four dogs before any cat |

- **Reproducibility bug found on the way — the embeddings weren't stable.** The `_quantized` exports use *dynamic* int8 quantization, whose scale is computed per input tensor: the same photo's embedding moved by up to **0.09 per coordinate** depending on how many images shared its batch, and the text tower gave different vectors on CoreML vs CPU. Prompt templating re-tested on the stable embeddings — still no gain.
- **Honest limit that remains:** for the bare word "airplane", B/16 ranks the aerial *airport* photo in the weak tier (correct demotion) but does not surface the vintage black-and-white plane-on-tarmac photo at all (distance 1.59); "an old propeller plane" or "a black and white photo of a plane" finds it first. **Weak tier made relative (2026-09-11, user's live test: "Aeroplane").** The British spelling is a rarer caption word for CLIP, so its text embedding is less specific and *everything* sits a little closer: the strong tier was right (both real planes, the wreck, the airport) but the "possibly related" band filled with 8 unrelated photos. **int8 quantization was distorting the embeddings — switched to fp16 (2026-09-11, user's re-check: "output is not up to the mark").** With three clear airliner photos added to the demo folder, "Airplane" still ranked a photo of children under a plane wreck above a Lufthansa jet against blue sky. | precision | size | ms/img | image-embedding agreement with PyTorch | distance error |
|---|---|---|---|---|
| int8 (was) | 152 MB | 33 | min 0.897, mean 0.963 | 0.021 mean / 0.111 max |
| **fp16 (now)** | 300 MB | 38 | 1.000 | 0.000 |
| fp32 | 599 MB | 30 | 1.000 | 0.000 |

## Phase 11 — Reliability & File Lifecycle ✅ (built and verified 2026-09-21)

- [x] **Crash recovery, no full rescan** — a record is written before its chunks (so the watcher and the scan can find it), so a crash between the two used to leave a record with the new hash and no chunks that every later scan skipped as "unchanged" forever. `files.indexed` (migrated in place with `ALTER TABLE`) is set only once the chunks are stored; on start `LiveIndexing` counts the unfinished records and the queued scans re-index exactly those — unchanged files are skipped on size + mtime, so recovery costs one stat per file. - [x] **Corrupt / unsupported files** — bad PDF/DOCX/XLSX/PPTX, zero bytes, binary-as-.txt, a 3 MB single line, a formula-injection CSV: each is counted, listed with its reason (`RECENT_FAILURES`, on the Status page under "Files that could not be indexed"), and never aborts the folder; known-bad content hashes are not re-parsed on later scans until the bytes change

Two tiny logistic regressions on the rule router's own features (numpy gradient descent, no sklearn, weights in JSON) give P(filename suffices) and P(keyword suffices); the cheapest tier over 0.6 confidence is taken, otherwise the rules decide. Exact phrases, filters-only queries and escalation are untouched, so a wrong cheap guess costs one extra pass, never a lost result

## Phase 18 — Query Router, Complexity Estimation & Reranker (Objective 3) ✅ (built and verified 2026-09-21)

Until this phase `search/service.py` ran the same pipeline for every query and the user picked Smart/Exact/Keyword by hand. Now `mode=auto` (the default) lets the router decide.

- [x] `search/router.py` — cheap surface features only (word count, content words, question words, unknown-to-the-index words, stopword ratio, clause count, and one in-memory filename probe); **tiers**: `filename` (≥ 2 words covering ≥ 75 % of a file name → names only, no models), `metadata` (filters only, no words → list matching files newest first), `keyword` (≤ 3 known words, no question → names + BM25, no embedding), `hybrid` (names + BM25 + embedding + RRF), `hybrid+rerank` (≥ 7 content words, ≥ 2 clauses, or a question with ≥ 5 content words → hybrid, then the cross-encoder). Complexity 0–3 and a plain-language `reason` on every decision. **Single words never take the names-only tier** — found by the live test: "sourdough" chose the guide *named* sourdough and dropped the recipe whose *content* says it
- [x] Metadata search beyond `type:` — `query_parsing.py` parses `ext:`, `after:2025[-03[-14]]`, `before:`, `size:>10mb` / `size:<500kb`, `in:folder`; `QueryFilters.matches()` narrows every tier's candidate set, and filters alone route to the metadata tier ("Matches filters: type pdf, after 2025-01-01" chip)
- [x] **Escalation**: when the chosen tier returns nothing confident, the service re-runs one tier up (`filename → keyword → hybrid → hybrid+rerank`), once; quoted phrases and manual modes never escalate. Verified: "sourdough balancer" (two known words BM25 cannot AND together) → keyword found nothing → hybrid found the recipe
- [x] **Cross-encoder reranker** — `search/reranker.py`, `ms-marco-MiniLM-L-6-v2` ONNX (91 MB, `scripts/download_reranker_model.py`, CPU, ~6 ms for 4 pairs), over the top 10 fused chunks, only on the top tier. `reranker_score` is finally non-null. **Two measured findings shaped its design** (both in `prototype_router.py`): (1) on this project's signature concept match — *"traffic spikes"* vs *"horizontal scaling when demand increases"* — it ranks the right passage **last**, below a recipe (ONNX output verified identical to the PyTorch reference, so it is the model, not the export): MS-MARCO cross-encoders reward answer-likeness, the bi-encoder is what catches concept matches; (2) as a mere third vote in RRF it was outvoted 2–1 by BM25 + embedding on exactly the queries it exists for (a to-do that *echoes the question* beat the invoice that *answers* it although the reranker scored the answer 6.7 vs 4.4). Final design: **promotion, not veto** — candidates the reranker judges relevant (logit > 0) are lifted above the rest, ordered by logit; when it judges none relevant it changes nothing. Result: the invoice wins, the concept match stays first, "Re-read by the reranker: relevant" chip on promoted hits
- [x] Every `/search` response carries `route: {tier, requested_tier, escalated, complexity, reason, features, stages[{stage, ms | skipped, hits…}], total_ms, corrected_query}`; the query event's meta records `route`, `escalated`, `complexity`, `total_ms` — Phase 20's evaluation reads the log. `/status.models.reranker` reports the loaded model
- [x] UI: **Auto (routed)** is the default mode, Smart/Exact/Keyword remain manual overrides; a route badge next to the model name shows *tier · ms · skipped n* (↑ when escalated) with the reason and per-stage timings in its tooltip; reranker and filter chips have their own icons
- [x] Tests: `prototype_router.py` (6 checks: 8 labelled queries → expected tier; filename tier runs no BM25/embedding/reranker and keyword tier no embedding, every ran stage timed; escalation; filters parsed/applied/alone; reranker promotion beats fusion on the invoice case and abstains on the concept match; manual modes bypass the router) in `run_all_phases.py` — **11/11**; `live_test_all_phases.py` Phase 18 check — **17/0/2**. Browser: "gym plan" → *filename · 16 ms · skipped 3*; the multi-part rent/deposit question → *hybrid + rerank · 60 ms*. Console clean. **Not yet clicked by a human in the real Tauri window**

## Phase 19 — Local LLM Agent: Strategy Selection & Reasoning (Objectives 1 + 3) ✅ (built and verified 2026-09-21)

The "agent" in the assignment title: a small local model that understands the question, chooses a retrieval strategy, calls our search as a tool, reads what came back and answers with citations — or says it could not find it. Offline; the retrieval system stays the core, the model sits on top.

- [x] Runtime: `llama-cpp-python` (compiled on this Mac; Windows wheels are a Phase 14 job), **Qwen2.5-1.5B-Instruct Q4_K_M** (1.0 GB, `scripts/download_llm_model.py`, `--size 3b` for the 2 GB build), CPU, 4 k context. Measured on this Mac: loads in 0.6 s, **35–48 tokens/s**. Loaded lazily on the first question (`/ask/status` reports availability); `models/llm/` must ship in Phase 14
- [x] `agent/tools.py` — the agent's tools are our own API: `search(query, mode, filters)` (→ numbered sources; a file keeps its number across searches so [n] is stable), `read_more(source)`, `context()` (Phase 17's session, topics, top files, injected into the first prompt). The model sees the whole matched chunk (`chunk_text`, up to 700 chars), never the 20-token BM25 snippet — found when the CSV's groceries row was cut off and the model rightly said "not there". `open_file` is deliberately not a tool: opening is the user's click on the cited card
- [x] `agent/loop.py` — planning turns in **JSON mode** (llama.cpp grammar-constrained): `{thought, action: search|read_more|answer, query, mode, filters}` — the `mode` choice **is** Objective 1's "identify the appropriate retrieval strategy"; then a streamed free-text answer citing `[n]`. Hard limits: 4 tool calls, 6 planning turns, 25 s. Every step is an event (`context, thought, tool_call, tool_result, answer_start, token, answer, done, error`) → `GET /ask` streams them as server-sent events; the query event records `route: agent`, tool calls and total ms for Phase 20
- [x] **Harness rules that turned a 1.5B model from 1/10 into 10/10 on the answer key** (each one measured, each one a check in `prototype_agent.py`): (1) filters the question never asked for are dropped (`type:pdf`, `date:2023` were invented on every turn) and a justified filter that finds nothing is retried unfiltered; (2) a manual mode that finds nothing falls back to auto routing — `keyword` ANDs every word, so "Wednesday training" found nothing in a file that says "Wednesday: back and biceps"; (3) a plan that repeats an identical search gets one whole-question auto search instead, then the planning limit ends it; (4) action aliases (`find`, `respond`, `provide`…) are accepted; (5) **no "say you couldn't find it" instruction in the answer prompt** — the model reached for that escape hatch with the answer in front of it; instead **grounding is the harness's job**: the sources an answer's own distinctive words trace to (tf overlap, numbers count double) are the judge — the model's `[n]` are kept when they agree, replaced when they don't (it cited the expenses sheet for "excess 350 euros" one time in ten), and an answer no source supports becomes "I couldn't find that in your files."; (6) **every figure in the answer must appear in a cited source** or the answer carries a warning — measured live: "610 euros" became "210 euros" while every other word matched
- [x] UI: **Ask** button / a leading `?` in the search box → `ui/AskPanel.tsx`: streamed answer with `[n]` chips, cited file cards (Open / Reveal), warnings, "How it got there" trace (thoughts, tool calls with query + mode + filters, results with route and ms), `n tool calls · s · local model`. A search whose route report says `suggest_ask` (a question the retrieval tiers could not answer confidently) shows an "Ask IntelliFile" chip; the overlay gets the compact panel
- [x] Tests: `prototype_agent.py` — part A, scripted model (8 checks: decomposition + read_more + citation verification + unjustified-filter drop; mode fallback + repeat fallback; figure check; call limit; no-sources → not found; malformed JSON; time budget); part B, the real model over 8 fixture files × **10 questions with an answer key: 10/10 cite the right file, 10/10 grounded, 10/10 traces show a strategy choice, mean ~10 s, max ~21 s** (skipped when no model). In `run_all_phases.py` — **12/12**; `live_test_all_phases.py` Phase 19 check (stream shape, citations exist, grounded ⇔ cited) — **18/0/2**. Browser: Ask mode streamed a cited answer with the trace; console clean. **Not yet clicked by a human in the real Tauri window**
- [ ] Honest limits (for Phase 20 and the write-up): a 1.5B model is loose with non-numeric facts the figure check cannot catch (it wrote "you fly on Wednesday" for a trip dated 12 May — the words all overlap a source, so grounding passed); the 3B build is the first thing to try if that matters on the grading laptop. **Improvement 7** added a premise check for the other blind spot — a confident answer to a question the files cannot answer (30-question key: false answers 3 → 1). ## Phase 20 — Agentic Evaluation: Routing vs. Always-Hybrid, Personalization Lift (Objective 3) ✅ (measured 2026-09-21)

The assignment asks for quality *and* efficiency; this phase produces the numbers — and changed two decisions. Everything below is reproducible: `scripts/eval_corpus.py` generates the corpus and query set, `scripts/evaluate_routing.py` and `scripts/evaluate_personalization.py` run in `run_all_phases.py` and write `backend/data/eval_*.json`.

- [x] **Corpus + query set**: 39 generated documents across six areas of one person's life (cooking, fitness, money, travel, engineering, home) in .md/.txt/.csv, two in an `invoices/` folder; **60 labelled queries** — 12 filename lookups, 8 with metadata filters (2 filters-only), 20 short keyword, 16 natural-language with few shared words, 10 multi-part questions with two relevant files. Relevance is per query; hit@k counts the first relevant file, `both@5` whether both relevant files of a multi-part question appear in the top 5.

### Routing — router vs. always-hybrid (median of 3 runs, same index, same models)

| Set | n | Pipeline | hit@1 | hit@5 | MRR | both@5 | mean ms | median ms | embedded |
|---|---|---|---|---|---|---|---|---|---|
| **All** | 60 | always-hybrid | 92% | 93% | 0.928 | 97% | 8.3 | 7.8 | 97% |
| **All** | 60 | **router** | **95%** | **97%** | **0.961** | **100%** | **6.0** | **3.1** | **43%** |
| filename | 12 | always-hybrid → router | 100% → 100% | | 1.000 → 1.000 | | 7.6 → **2.8** | | 100% → **0%** |
| metadata | 2 | always-hybrid → router | 0% → **100%** | | 0.000 → **1.000** | | — | | 0% → 0% |
| keyword | 20 | always-hybrid → router | 100% → 100% | | 1.000 → 1.000 | | 7.3 → **2.5** | | 100% → **0%** |
| hybrid | 26 | always-hybrid → router | 88% → 88% | | 0.910 → 0.910 | | 10.0 → 10.4 | | 100% → 100% |

**The router keeps 104% of always-hybrid's MRR at 72% of its mean latency (28% saved), runs the embedding model for 43% of queries instead of 97%, and picked the labelled tier for 60/60 queries with 0 escalations.** It *beats* always-hybrid because filters-only queries (`type:csv`, `in:invoices`) have no text for the hybrid pipeline at all. On the two cheap tiers — 32 of 60 queries — latency drops ~65% at identical quality; on the hybrid tier nothing changes because the same work runs. Misses (2/60, both hybrid): "when is the car due at the mechanic" rank 6, "how should the shop's pages be released safely" not in top 10 — genuine bi-encoder limits, listed for Phase 15.

### Reranker — hybrid vs. hybrid + rerank on the 10 multi-part questions

| Pipeline | hit@1 | hit@5 | MRR | both@5 | mean ms |
|---|---|---|---|---|---|
| hybrid | 100% | 100% | 1.000 | 100% | 8.5 |
| hybrid + rerank (promotion) | 100% | 100% | 1.000 | 100% | 24.0 |

**Decision changed by the data:** chosen by query length, the rerank tier cost +15 ms on a sixth of the queries and changed no result where fusion was already confident (promotion only lifts what the cross-encoder judges relevant, and fusion was already right). The reranker is now reached **only by escalation** from hybrid when nothing is confident (`router.py`; `prototype_router.py` check 5 exercises the stage with the plan forced). The one case it demonstrably fixes — a note that *echoes* a question beating the file that *answers* it — stays covered by that check. Live router statistics on the real 307-file index agree: filename 4.5 ms, keyword 8.7 ms, hybrid 30 ms, hybrid+rerank 110 ms per query.

### Personalization — lift on ambiguous queries vs. harm on the rest

18 queries were made ambiguous by giving 8 documents a near-identical "old copy" twin; a synthetic four-week log opens the originals (four daily, four on Monday mornings), never the twins. The other 42 queries have no twin.

| Personalization | habitual original first | original above twin | MRR of original | others: MRR | others: same top-5 set & tiers |
|---|---|---|---|---|---|
| off | 44% | 50% | 0.694 | 0.956 | — |
| **on** | **78%** | **83%** | **0.861** | **0.956** | **42/42** |

**Decision changed by the data — the boost weight.** Sweep of `PERSONAL_WEIGHT` (lift on the 18 ambiguous vs. harm on the 42 others): 0.004 (the Phase 17 guess) → 94% first but **4/42 ordinary queries pushed down**; 0.002 → 94%, 3 harmed; 0.001 → 83%, 3 harmed; 0.0005 → 78%, 1 harmed; **0.00025 → 78%, 0 harmed**. Neighbouring RRF ranks differ by ≈0.00026, so at 0.00025 a habit can swap two neighbours but never leapfrog a clearly better match. Most of the lift comes from a rule added here: filename matches keep coverage order, but a habit now **breaks a tie** between names the query covers equally ("gym plan.txt" vs "gym plan (old).txt"). Shipped: 0.00025 — no harm wins.
